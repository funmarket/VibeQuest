# Database and public Places contract

Foundation has one PostgreSQL/PostGIS system of record and one public read authority. Web and Telegram consume the same `/v1/places` contract through `@vq/api-client`; neither client imports database code. `@vq/contracts` owns strict input/output schemas and the `PlacesRepository` port. The Fastify Places HTTP adapter validates query input and invokes the injected Places application query. That query owns output validation/unavailable errors and invokes the published-read port; the database package implements that port. The app composition root wires these capabilities, with no HTTP-to-private-repository shortcut.

`places` contains UUID `id`, nonempty `name` and `category`, `geometry(Point,4326)` location, `publication_status` (`draft`, `published`, `archived`), and UTC creation/update timestamps. Coordinate checks reject points outside legal longitude/latitude ranges. A partial GiST index covers published locations. A database trigger updates `updated_at`; the migration inserts no Place seed records. Identity, Profile, Media, Business, Activities, Events and Social tables now exist through migration 0013; wallet/check-in capabilities remain unfinished.

`GET /v1/places` requires `west`, `east`, `south`, `north`, with ordered nonzero spans of at most five degrees. Longitude ranges from -180 to 180, latitude -90 to 90. `limit` defaults to 50 and accepts integers 1–100. Optional literal case-insensitive name substring `q` (1–120 characters) and exact `category` (1–60) filters are parameterized by Drizzle SQL. Unknown input keys, duplicate arrays, empty strings, invalid numbers and overly broad viewports fail with 400 before repository access. The initial contract excludes antimeridian-crossing viewports; clients must submit an ordered bounded viewport.

`ST_Covers(ST_MakeEnvelope(...,4326),location)` includes exact boundary points and excludes outside/draft/archived places. Results sort by descending `created_at` with UUID tie-breaking. DTOs contain only `id`, `name`, `category`, `longitude`, `latitude`, `createdAt`, `updatedAt`; timestamps are normalized to ISO8601. Successful empty data returns `{places:[]}`. Database/query/output failures return 503 with `PLACES_UNAVAILABLE` and `Places are temporarily unavailable.` SQL details stay in server logs. The client rejects HTTP failures and validates successful responses; it never converts errors to fabricated empty success.

`pnpm db:migrate` requires a PostgreSQL `DATABASE_URL`. The runner uses one transaction and a transaction advisory lock, records migration filename/SHA256, skips unchanged applied files, and rejects altered applied migrations. Failed DDL rolls back with its ledger entry. Migrations create schema only, with no production seed. `postgis` installation requires an appropriate migration role. Production runtime permissions must support the implemented owners' authorized reads/writes without migration privileges; a read-only role suffices only for the Places reader. Role provisioning remains a separately authorized infrastructure operation. No infrastructure or remote database was provisioned here.

The API validates required database URL/port at startup, binds loopback port 4100 by default, uses structured logs and bounded connection/query/request timeouts, and closes HTTP/database resources on SIGINT/SIGTERM. `/health/live` reports process availability; `/health/ready` executes a real schema query and returns 503 when unavailable. A generic API built without a readiness dependency returns 503 for readiness.

R38 plans additive Identity-owned persistence for Telegram user associations and secure account linking. One Telegram identity must resolve to at most one canonical `identity_users.id`, with database-enforced uniqueness and atomic first-launch provisioning. Existing `identity_users` and domain-owned foreign keys remain authoritative. Telegram-first canonical users must not depend on possessing a password account. Existing migrations `0001`–`0013` remain immutable. Exact new tables, columns, indexes and migration numbers require separate implementation authorization.

All thirteen SQL files are present in `packages/database/migrations`. Filename alone does not imply table ownership: 0005 includes Profile and Media state; 0008 includes Identity privileges and Business state. Preserve applied files exactly and add migrations only in an authorized implementation packet. Current database application state was not queried during D01.

Repositories use parameterized SQL/Drizzle and owner-specific transactions. Constraints, version checks and locks protect implemented mutation flows; referential links do not permit foreign table writes. Social uniqueness/self-follow checks, Activity/Event attachment foreign keys and scoped privilege checks are implementation boundaries, not a universal production scalability claim. See owner implementation reports and [domain ownership](domain-ownership.md).

[Local development](../operations/local-development.md) explains explicitly selected migration/test databases and environment handling. No separate PostgreSQL authority, Telegram-only business tables, browser-local canonical state or original Supabase/Firebase/Firestore backend is permitted.

## Approved future persistence boundaries — no migration yet

The [open-first/live Places addendum](../product/OPEN_FIRST_LIVE_PLACES_FOUNDATION_DECISIONS_2026-10-10.md) changes future design, not current schema. Anonymous public reads must not create `identity_users` or fake guest/reward records. Identity owns the future server-verified Telegram association and explicit Web link; the prospective administrator handle does not create an admin row or privilege. A future R42 privilege bootstrap must verify a canonical user and be audited, not inferred from a username. Existing migrations remain checksummed and immutable.

Future R29 Place Contributions needs durable, author-linked **atmosphere observations** separate from factual place corrections, including a normalized HighVibes/Vibing/LowVibes value, event time, permitted confidence/evidence provenance, moderation visibility and historical read rules. A derived *current* Vibe view uses a few-hour eligibility window and reports insufficient data honestly; records persist for permitted historical browsing after they cease influencing the meter. Proposed tables, retention periods, confidence weights, anti-abuse constraints and uniqueness are not settled or installed. Places remains the canonical venue reference; Geo retains consent/evidence authority. R31 nearby-city pulse consumes aggregated authorized signals; R32 Trails retains ordered destination/link/notes records referencing canonical Places rather than copying venue coordinates as a separate authority. Add only owner-approved migrations when implementing each domain. Redis is never the canonical store for these records.
